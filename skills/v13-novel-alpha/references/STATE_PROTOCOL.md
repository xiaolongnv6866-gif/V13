# V13 ALPHA 事件化世界状态协议

**原则**：记录“已经发生”而非“作者希望后来发生”。绝对数字和证据分离；小说人物所见与世界事实分离；对纸面应收到货与实际现货分户记账。

## 文件和解释

`templates/STATE_TEMPLATE.json` 提供可被 `scripts/validate_state.py` 机械核验的数据结构，`fixtures/chaoxun_ch03.json` 是由实际完成的原创《潮汛账》前三章整理的测试实例。这是实验合同，不是明代制度实证。

- `initial_accounts`：各类可数账户的零点余额。库存、现银、应收、未到承诺、欠薪至少要使用不同账户名；脚本不会把任意账户自动视作同一种资产。
- `events`：以顺序记录时间、发生章节、现场证据（自己作品中真实可定位的段落文件）、各账户变动、所需授权与独立事实更新。余额只通过事件算得，不能在终态另写一个相互矛盾的数。
- `permissions`：授予者、对象、有效章区间、限量、用途。支付工资和开仓可以有不同的来源凭据；有许可不等于一定已执行，动作事件才扣账。
- `facts`：`CONFIRMED`／`REPORTED`／`HEARSAY`／`INFERRED`／`UNKNOWN`。真实世界是否核实，要有 `source` 及证据；角色断言并不将事实自动升级。
- `characters`：各人的 `knows`／`heard`／`believes` 与未偿目标。主角不能因为作者看过上一章敌人视角而拥有相同知识。
- `open_loops`：因果责任、欠付和关系债，不可只留下“后面有大战”式抽象悬念。

## 不能自欺的检查

负余额、先执行后授权、超授权数量、章序倒退、无出处将传闻标为`CONFIRMED`、重复事件ID、同一交易多次扣款都要机械拒绝。工具对抽象事实的真伪仍**无法**独立核实；有`source`只能说明有人写了引用，不能代替文学与历史审查。

四个状态尤其不得混同：`planned`（打算）→`promised`（被承诺）→`authorized`（被允许）→`executed`（实际完成）。一个人喊“我已经批了”不等于银子到账；银子确实收到须另建`event`并加现场证据。

## 合法续写

先读最后已确认账户、人物信息与未偿事件；只能在新增事件有证据时改变余额。故事可把原有猜测写成被证实，但必须增加亲眼核验或可信外部证据和接受者；不能为了让剧情走快而把`HEARSAY`改成`CONFIRMED`。

数据协议只能判断逻辑约束，不能替代好小说的动机、冲突、喜剧/悬念、文化厚度和审美评审。

## ALPHA 资源正向变更的入账门

从CH05起，任何实物干/湿粮正向变化必须有`RECEIPT`或`DONATION_RECEIPT`事件和`receipt_evidence_ref`；公银正向变化需`CASH_RECEIPT`或`CASH_RETURN`及收银证据。承诺转为现货仍需同数额守恒。工具只能验证凭证字段与状态结构，无法证明真实历史收据有效，也不能凭此宣布独立文学验证。
